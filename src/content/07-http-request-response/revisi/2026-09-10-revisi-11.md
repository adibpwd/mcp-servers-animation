## 🔍 Analisis Masalah

### Masalah 1 — Analogi "Browser = Tukang Pos" Salah Posisi

**Kondisi sekarang:** `HOOK_REVEAL = 'Browser = Tukang Pos! 📬'`

Browser diposisikan sebagai *tukang pos* (kurir), tapi kurir seharusnya
adalah pihak yang membawa surat dari pengirim ke penerima — bukan
pengirim itu sendiri. Kalau browser = tukang pos, maka:
- Siapa yang nulis suratnya?
- Kenapa tukang pos yang nerima balasannya kembali?

Ini yang terasa "aneh": tukang pos itu one-way delivery agent, bukan
pengirim yang juga menerima balasan.

**Posisi yang lebih akurat:**
- **Browser = Penulis surat (pengirim)** — dia yang inisiatif kirim request
- **Jaringan/internet = Kurir** — yang membawa paket ke tujuan dan balik lagi
- **Server = Penerima + penulis balasan** — buka surat, proses, kirim balik

Atau kalau mau tetap pakai metafora kantor pos:
- **Browser = Pelanggan di kantor pos** — yang datang minta kirim surat
- **Internet/DNS = Sistem pengiriman kantor pos** — routing & alamat
- **Server = Kantor pos tujuan / penerima** — yang proses dan kirim balik

**Fix:** Ganti `HOOK_REVEAL` dari `'Browser = Tukang Pos!'` ke sesuatu
yang memposisikan browser sebagai *pengirim*, bukan kurir. Opsi:
`'Browser kirim surat, bukan comot langsung.'` (sudah ada di plan awal
`_docs/HTTP_REQUEST_RESPONSE_PLAN.md` §Act 1 Payoff — tinggal restore).

### Masalah 2 — "Surat Siap!" Prematur (Sebelum Proses Selesai)

**Kondisi sekarang:** `ENVELOPE_SEALED_CAPTION = 'Surat siap! ✉️'`

Ini muncul di beat 4 Act 1 (t≈+5.8s lokal, ~t=12.5s absolut) — saat
amplop *request* tersegel. Tapi Act 2 dan 3 sesudahnya masih membahas:
DNS lookup → koneksi ke server → server proses → server buat response.

Kata **"siap!"** dengan tanda seru implisit "semua sudah selesai",
padahal ini baru awal perjalanan — request baru siap *dikirim*, belum
ada response sama sekali. Ini misleading secara narasi.

**Perbedaan semantik yang diinginkan:**
- Yang sekarang: "Surat siap!" → kesan "selesai"
- Yang benar: amplop tersegel = request siap *berangkat*, bukan selesai

**Fix:** Ganti `ENVELOPE_SEALED_CAPTION` jadi kata yang menunjukkan
ini *awal perjalanan*, bukan akhir. Opsi:
- `'Surat berangkat!'` — aktif, menunjukkan mau pergi
- `'Request dikirim.'` — lebih netral/teknis
- `'Surat dalam perjalanan.'` — eksplisit masih on-the-way

Rekomendasi: **`'Surat berangkat!'`** — pendek, aktif, dan jelas bahwa
perjalanan baru mulai (bukan selesai).

### Masalah 3 — HTML/JS/CSS Tiba-Tiba Muncul di Browser (Tidak dari Server)

**Kondisi sekarang:** Di Act 5 (gabungan Act 4+5 lama: "Surat Diproses
& Distempel"), fokus visualnya ke status code (stempel 200/404/500) +
amplop response tersegel lalu terbang balik ke browser. Di Act 6,
`rawStatusChip`, `rawHeaderChip`, `rawBodyChip` muncul saat amplop
dibuka — lalu transform jadi `pageContent` (halaman jadi).

**Gap naratif:** Penonton tidak pernah melihat server *memasukkan*
file HTML/CSS/JS ke dalam amplop response. Asset-asset itu seolah
"muncul sendiri" di browser saat amplop dibuka, tanpa ada konteks
visual "ini dikirim dari web server".

Secara teknis: web server mengambil file HTML (dan referensi ke CSS/JS),
memasukkannya ke response body, baru disegel dan dikirim. Proses ini
hilang sama sekali dari animasi saat ini.

**Fix:** Tambahkan beat kecil di Act 5 (sebelum amplop response
disegel) yang menunjukkan server *mengumpulkan asset* dan memasukkannya
ke amplop:
- Icon `html-document`, `css-document`, `js-document` muncul dari
  ikon server/gedung dengan animasi "keluar dari server" (fly ke amplop
  response, atau scale-in di dalam amplop)
- Baru setelah itu amplop disegel + stempel status dijatuhkan
- Di Act 6, saat amplop dibuka, chip-chip itu sudah ada konteksnya:
  "ini yang dikirim server tadi"

Dengan ini alur jadi lengkap:
```
Server proses → kumpulkan HTML/CSS/JS → masukkan ke amplop →
stempel status code → kirim balik → browser buka amplop → render
```
