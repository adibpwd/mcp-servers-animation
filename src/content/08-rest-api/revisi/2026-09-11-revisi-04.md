## Masalah

Alur utama sudah menjelaskan `GET /users` sampai response `200`, tetapi
epilog hanya menampilkan `POST` dan `DELETE`. Penonton belum melihat
`PUT`, sehingga representasi method REST belum lengkap.

## Keputusan

Alur utama tidak diubah: `GET /users` tetap menjadi contoh yang mengikuti
perjalanan client → endpoint → server → client. Setelah hasil GET tiba di
client, `resultCard` yang sama berubah berurutan agar memperlihatkan:

| Method | Status | Makna visual |
|---|---:|---|
| GET | 200 | Mengambil data — alur utama Act 1–4 |
| POST | 201 | Data dibuat |
| PUT | 200 | Data diperbarui |
| PATCH | 200 | Data diubah sebagian |
| DELETE | 204 | Data dihapus |

`PATCH` ditambahkan sebagai pelengkap umum untuk perubahan parsial; inti
CRUD (`GET`, `POST`, `PUT`, `DELETE`) tetap tampil seluruhnya.

## Batasan

- Tidak membuat perjalanan request baru untuk setiap method, supaya durasi
  tidak membengkak dan alur utama tetap mudah diikuti.
- Tidak membuat card baru: satu `resultCard` persisten di-*morph* melalui
  helper `morph()`.
- Durasi Act 5 naik dari 7 ke 9 detik. Total video menjadi 54 detik,
  masih dalam target 45–55 detik.

## Tindak Lanjut — Tempo Lebih Cepat + Data Berbentuk Objek

### Tujuan

Animasi dari Act 1 hingga penutup terasa sedikit terlalu lama, terutama
pada jeda setelah sebuah aksi selesai. Selain itu, `User #42` masih
terasa seperti teks data abstrak. Rencana ini membuat ritmenya lebih
padat dan mengubah data menjadi objek visual tanpa menampilkan JSON.

### Keputusan Konsep: Kartu Anggota di Lemari Data

Gunakan **kartu anggota fisik** sebagai representasi resource `/users`.
Server memiliki lemari kartu; satu kartu berisi avatar sederhana, nama,
dan badge status. Ini tetap merepresentasikan data user, tetapi penonton
bisa melihat akibat tiap HTTP method secara langsung.

| Method | Aksi pada kartu | Hasil yang terlihat |
|---|---|---|
| GET | Ambil kartu `User #42` dari lemari | Kartu keluar dan dikirim ke client |
| POST | Masukkan kartu anggota baru | Kartu baru masuk ke slot; status `201` |
| PUT | Ganti satu kartu dengan versi lengkap baru | Kartu lama dibalik/diganti penuh; status `200` |
| PATCH | Ubah satu bagian kecil pada kartu | Badge status atau nama mendapat stempel/edit; status `200` |
| DELETE | Tarik kartu dari lemari ke tempat arsip | Slot menjadi kosong; status `204` |

`PUT` dan `PATCH` sengaja dibedakan secara visual: PUT mengganti seluruh
kartu, sedangkan PATCH hanya mengubah satu badge/field. Dengan begitu,
makna update penuh vs parsial dapat dipahami tanpa penjelasan JSON.

### Perubahan Struktur Visual yang Direncanakan

1. Resource dots `User 01–03` diganti menjadi tiga slot kartu kecil di
   dalam lemari server.
2. `User #42` diganti menjadi kartu anggota yang dapat diangkat,
   dibalik, diberi badge, diganti, atau disingkirkan.
3. Response `GET` membawa miniatur kartu, bukan label `User data`.
4. Act 5 tidak hanya mengganti teks pada `resultCard`: setiap method
   memicu micro-animation pada kartu/slot yang sama. Tidak ada perjalanan
   request penuh yang diulang.
5. Tetap gunakan `GET /users` pada alur utama agar cerita inti tidak
   berubah; Act 5 menjadi demonstrasi aksi lain terhadap koleksi kartu.

### Rencana Percepatan Tempo

Target baru adalah sekitar **46 detik** dari 54 detik saat ini (±15%
lebih cepat). Pengurangan dilakukan pada hold/jeda kosong, bukan dengan
mempercepat pop-in, morph, atau perjalanan request sampai sulit dibaca.

| Act | Saat ini | Target | Cara mempercepat |
|---|---:|---:|---|
| 1 — Client meminta data | 11s | 10s | Kurangi jeda sebelum request keluar dari client |
| 2 — Menuju endpoint | 10s | 8s | Pangkas hold setelah endpoint menerima request |
| 3 — Server memproses | 13s | 11s | Rapatkan jeda setelah kartu dipilih dan response siap |
| 4 — Response kembali | 11s | 9s | Pangkas hold sesudah client menerima hasil |
| 5 — Method lain | 9s | 8s | Padatkan jeda antar-method, tetap beri waktu baca |
| **Total** | **54s** | **46s** | **Lebih responsif, tetapi tiap aksi masih terbaca** |

Untuk Act 5, setiap method tetap menerima sekitar 1,25–1,4 detik layar
aktif, lalu transisi morph yang singkat. Urutannya tetap
POST → PUT → PATCH → DELETE sebelum kembali ke GET.
