## 1. Empat masalah (bukan tiga)

### Bug A — Presence Jokowo/Prabowo tampil dari Act 1
`Animation.jsx` baris state: `useState(true)` untuk `jokowoPresent` dan
`prabowoPresent`, dan di reset loop timeline juga di-set `true`. Padahal
POST baru terjadi di Act 3. Root cause: nilai awal salah, bukan salah di
`applyMutation()` (itu sudah benar — insert baru set true saat POST).

### Bug B — Tidak ada fetch-ulang (GET) setelah POST
Semantik REST asli: response POST 201 memang boleh balikin representasi
resource baru, TAPI keputusan produk (lihat komentar data.js REVISI-08)
adalah browser harus **GET terpisah** supaya jelas kartu profil = hasil
fetch, bukan otomatis "nempel" begitu dibuat. Saat ini `REQUESTS` cuma
punya `POST_JOKOWO`/`POST_PRABOWO`, tidak ada `GET_JOKOWO`/`GET_PRABOWO`.
Timeline Act 3 juga cuma panggil `sendRequest` untuk POST, tidak ada
langkah fetch susulan. Ini kenapa PHASES sudah dinaikkan ke 18s durasi
Act 3 di data.js (§0) — durasi sudah dianggarkan, tapi request objectnya
belum dibuat dan timeline belum dipanggil.

### Bug C — Warna intro belum pakai tema NETWORKING
Di JSX header: `<tspan fill={COLORS.CLIENT}>REST</tspan> <tspan
fill={COLORS.SERVICE}>API</tspan>` — masih CLIENT (sky lama, kebetulan
sama hex-nya dengan NETWORKING_SKY) dan SERVICE (amber). Sesuai
`revisi-07.md` §2 palet intro: REST = mint `NETWORKING_MINT`, API = sky
`NETWORKING_SKY`. Saat ini "REST" salah warna (amber-adjacent scheme
lama), cuma "API" yang kebetulan benar karena CLIENT dan NETWORKING_SKY
sama-sama `#38BDF8`.

### Bug D — `browserLoading` di-set tapi tidak pernah dibaca render
`applyMutation()` sudah benar set `setBrowserLoading(false)` saat GET
Adib selesai (action `read`). Tapi tidak ada satupun tempat di JSX yang
membaca `browserLoading` untuk kondisional render. Profil Adib (nama,
usia, role, rambut, avatar) langsung dirender penuh sejak awal mount,
padahal `revisi-07.md` §4 mewajibkan skeleton/spinner dulu sebelum GET
200 kembali.

## 6. Bug E — Panel Browser "Hydrate" Terlalu Awal (ditemukan pwd2y
   pasca-eksekusi §1-5, sistemik di SEMUA request)

### Simptom yang dilaporkan
Saat GET (Act 1-2): request masih "diproses" di API Service Hub (ticket
masih di compartment GATE/PROCESSOR, response BELUM dibuat, apalagi
belum melaju balik) — tapi data Adib sudah muncul penuh di panel
browser. Harusnya panel browser baru "tahu" isinya setelah response
benar-benar tiba, bukan bocor duluan dari sisi server.

### Root cause (satu titik, dampak ke SEMUA request)
`resolveFlow()` cuma punya SATU titik waktu mutasi:
~~~
t += holdBeforeProcessor
tl.add(() => applyMutation(req), t)   // ← SEMUA state berubah di sini
...
t += cardHold
tl.add(() => setRespVisible(true) ...)         // response BARU dibuat
...
back = travel(setRespY, PROCESSOR→CLIENT, 1.35) // response BARU sampai
tl.add(() => { ...; setBrowserView(...) }, back)
~~~
`applyMutation(req)` isinya campur dua kelas state yang seharusnya beda
waktu:
- **Server/cabinet-facing** (representasi "API Service sudah punya data
  baru") — WAJAR berubah di `t`, karena memang di titik itu server
  "commit" perubahan.
- **Browser-panel-facing** (apa yang DILIHAT user di browsernya) — HARUS
  berubah di `back`, bukan di `t`, karena secara naratif browser belum
  "tahu" apa-apa sampai response-nya sendiri tiba.

Semua 6 request lewat fungsi yang sama, jadi bug ini otomatis kena ke
semuanya, bukan cuma GET. Rincian per request:

| Request | State yang di-set di `applyMutation` | Kelas | Status |
|---|---|---|---|
| GET | `setBrowserLoading(false)` | browser-panel | 🐛 kepagian di `t` |
| POST_JOKOWO | `setJokowoServerExists(true)` | server/cabinet | ✅ benar di `t` (server commit) |
| POST_PRABOWO | `setPrabowoServerExists(true)` | server/cabinet | ✅ benar di `t` |
| GET_JOKOWO | `setJokowoCardVisible(true)` | browser-panel | 🐛 kepagian di `t` |
| GET_PRABOWO | `setPrabowoCardVisible(true)` | browser-panel | 🐛 kepagian di `t` |
| PUT | `setAdibHair(newHair)` | **dobel dipakai**: cabinet (`cabinetSlots` map) DAN browser panel (`HAIR_HEX[adibHair]`, teks rambut) | 🐛 browser-sisi kepagian; cabinet-sisi sebenarnya benar |
| PATCH_JOKOWO | `setJokowoRole(newRole)` | **dobel dipakai**: cabinet DAN mini-card `jokowoCard` (`{jokowoRole}`) | 🐛 mini-card-sisi kepagian; cabinet-sisi benar |
| DELETE_PRABOWO | `setPrabowoServerExists(false)` + `setPrabowoCardVisible(false)` | server/cabinet (benar) + browser-panel (salah) | 🐛 separuh kepagian |

Juga `popInIds` (pop-in animasi `jokowoCard`/`prabowoCard`) di-trigger di
`t` yang sama (lihat §Checklist Revisi-08 sebelumnya) — begitu
`jokowoCardVisible`/`prabowoCardVisible` dipindah ke `back`, trigger
pop-in-nya WAJIB ikut pindah ke `back`, kalau tidak animasinya jalan
duluan sebelum boolean-nya `true` (state mismatch, popIn kebuang).

### Insight tambahan: ini justru bisa jadi FITUR naratif kalau dibenerin
benar. PUT dan PATCH itu contoh paling jelas: kalau cabinet (server)
di-update di `t` TAPI panel browser masih nunjukin nilai LAMA sampai
`back`, itu justru mengajarkan semantik REST yang akurat — "server
sudah punya data baru, tapi client belum refresh viewnya sampai response
diterima". Ini alasan kenapa fix-nya BUKAN cuma "pindahin semua ke
`back`", tapi perlu split jadi 2 fase dengan state yang sebagian dobel.

### Rencana perbaikan

1. **Pecah `applyMutation()` jadi 2 fungsi**:
   - `applyServerMutation(req)` — dipanggil di `t` (waktu sekarang).
     Isinya HANYA state yang scope-nya cabinet/server:
     `jokowoServerExists`, `prabowoServerExists` (insert/archive), dan
     dua state BARU `adibHairServer`/`jokowoRoleServer` (dipakai KHUSUS
     oleh `cabinetSlots` map, supaya cabinet boleh berubah lebih dulu).
   - `applyBrowserHydrate(req)` — dipanggil di `back` (BARU, titik waktu
     response benar-benar tiba). Isinya SEMUA state yang scope-nya
     panel browser: `browserLoading`, `jokowoCardVisible`,
     `prabowoCardVisible`, dan dua state BARU
     `adibHairDisplayed`/`jokowoRoleDisplayed` (dipakai KHUSUS oleh
     render `browserPanel` dan mini-card `jokowoCard`).
2. **State yang perlu di-split jadi 2 varian** (karena dipakai di 2
   tempat dengan 2 timing berbeda):
   - `adibHair` → `adibHairServer` (cabinet, update di `t`) +
     `adibHairDisplayed` (browser panel, update di `back`). Render
     cabinet pakai `adibHairServer`; render `browserPanel`/`HAIR_HEX`
     pakai `adibHairDisplayed`.
   - `jokowoRole` → `jokowoRoleServer` (cabinet) + `jokowoRoleDisplayed`
     (mini-card `jokowoCard`). Sama pola.
   - `jokowoCardVisible`/`prabowoCardVisible`/`browserLoading` TIDAK
     perlu split (memang cuma dipakai di browser panel) — cukup pindah
     titik `setState`-nya dari `applyServerMutation` ke
     `applyBrowserHydrate` (dari `t` ke `back`).
3. **Wiring di `resolveFlow()`**: ganti
   `tl.add(() => applyMutation(req), t)` jadi
   `tl.add(() => applyServerMutation(req), t)`, lalu tambah
   `applyBrowserHydrate(req)` di DALAM `tl.add()` yang sudah ada di
   `back` (yang sekarang isinya `setRespVisible(false); ...;
   setBrowserView(...)`) — supaya tidak nambah `tl.add()` baru, cukup
   numpang di callback yang sudah ada persis di waktu yang tepat.
4. **`popInIds` ikut pindah**: `popInIds.forEach(id => popIn(tl, t, id,
   ...))` di `resolveFlow()` pindah dari argumen di sekitar `t` ke
   argumen baru `popInIds` yang dieksekusi di `back` (butuh parameter
   terpisah, atau reuse `popInIds` yang sama tapi posisi `tl.add`/`popIn`
   call-nya dipindah ke blok `back`).
5. **Reset loop**: tambah `adibHairServer`/`adibHairDisplayed` dan
   `jokowoRoleServer`/`jokowoRoleDisplayed` ke reset (keduanya reset ke
   nilai awal `ADIB_PROFILE.hair`/`JOKOWO_PROFILE.role`), ganti nama
   lama `adibHair`/`jokowoRole` di reset block.
6. **`cabinetSlots` map**: ganti `hair: adibHair` → `hair:
   adibHairServer`, `role: jokowoRole` → `role: jokowoRoleServer`.
7. **Render `browserPanel`**: ganti `HAIR_HEX[adibHair]` dan teks
   rambut → pakai `adibHairDisplayed`.
8. **Render mini-card `jokowoCard`**: ganti `{jokowoRole}` →
   `{jokowoRoleDisplayed}`.
